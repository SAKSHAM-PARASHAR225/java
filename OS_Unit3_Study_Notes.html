RAID Structure & Levels

Definition — RAID RAID (Redundant Array of Independent Disks) combines multiple small, inexpensive disk drives into an array that appears to the OS as one single logical storage unit. It improves performance, fault tolerance, and storage capacity. This is an example of storage virtualization.

Why RAID?

Performance
Overlapping I/O operations across disks increases data throughput. Multiple disks serve read requests simultaneously.
Fault Tolerance
Redundant data means one disk can fail without data loss. Increases MTBF (Mean Time Between Failures).
Capacity
Logical volume appears larger than any single physical disk. Scales by adding drives to the array.

Key Techniques

Striping (RAID 0)

Data is partitioned across multiple drives into stripes (512 bytes to several MB). All stripes written simultaneously → high throughput. No redundancy — any single disk failure = total data loss.

Mirroring (RAID 1)

Every write goes to two or more disks simultaneously (100% duplication). Excellent fault tolerance — if one disk fails, the mirror continues. High cost: 50% of storage is redundancy overhead.

  • RAID 5 rebuild risk: While rebuilding after a failure, if a second disk fails, all data is lost.
  • RAID 1 cost: 50% of total disk capacity is used for redundancy.
  • RAID ≠ Backup: RAID protects against hardware failure but NOT accidental deletion, corruption, or ransomware.

File Concepts & Access Methods

Definition — File A file is a named collection of related information stored on secondary storage. It is the smallest unit of logical secondary storage. The OS abstracts physical storage media into logical files and provides a uniform interface to access them.

File Attributes

AttributeDescription
NameHuman-readable string identifier (e.g., example.c). Once named, file is independent of process/user/system.
IdentifierUnique tag/number identifying the file within the file system (inode number in Unix).
TypeFile type indicator (.txt, .exe, .jpg). Needed by OS that supports multiple types.
LocationPointer to device and location of file on that device.
SizeCurrent size in bytes/words/blocks; maximum allowed size.
ProtectionAccess-control info: who can read, write, execute.
Time & User IDCreation, last modification, last use timestamps; owner identification.

File Operations

  • CreateAllocate space in file system, make directory entry.
  • WriteOS searches file by name, maintains write pointer; writes data.
  • ReadSearches file, maintains read pointer; reads data into buffer.
  • RepositionRepositions file pointer to a given value (seek). No I/O needed.
  • DeleteSearches directory, releases file space, erases directory entry.
  • TruncateErases file contents but keeps attributes. Resets file length to 0.

Access Methods

Sequential Access

Simplest method. Reads records one after another in order. File pointer advances automatically. Typical for compilers, batch jobs.

read_next() → advances pointer
write_next() → appends to end

Direct (Relative) Access

File is a numbered sequence of fixed-length logical records. Programs can read/write in any order. Based on disk model (random access). Used in databases.

read(n) → read block n
write(n) → write to block n

Index Access

Built on top of direct access. An index holds pointers to various blocks. To find a record: search index → use pointer to access block. Used for very large files.

search_index(key)
→ pointer → read_block(ptr)

File Allocation Methods

Definition — Allocation Method Defines how disk blocks are assigned to files. The choice affects disk utilization, file access time, and susceptibility to fragmentation.

1. Contiguous Allocation

Each file occupies a set of contiguous (adjacent) blocks on disk. Requires only the starting block number and the length.

Pros: Simple, excellent sequential AND random access performance (best I/O). Easy to implement.

Cons: External fragmentation over time. Must know file size in advance. Compaction needed (expensive downtime).

Each file is a linked list of disk blocks scattered anywhere on disk. Each block contains a pointer to the next block. Last block has nil pointer.

Free Space Management

Definition The OS must track which disk blocks are free so they can be allocated to new files. Several techniques exist, each with different time/space trade-offs.

Bit Map (Bit Vector)

One bit per block. 0 = free, 1 = occupied (or vice versa). Easy to find contiguous free blocks using bitwise operations. Requires extra space (e.g., 1 GB disk with 4KB blocks → 32,768 bit = 4 KB bitmap).

00111100 10000011 ...
↑ free blocks at position 0,1,6,7...

Linked List

All free blocks linked together. First free block contains a pointer to the next free block, etc. Simple but traversal is expensive — must read each block to find the next free one. Not efficient for finding contiguous blocks.

Grouping & Counting

Grouping: First free block stores addresses of next n−1 free blocks + pointer to next such group.
Counting: Store (address, count) pairs — "n contiguous free blocks starting at address X." Efficient when files are contiguously allocated.

Protection & Access Matrix

Definition — Protection Protection ensures that each object (hardware or software resource) is accessed correctly and only by authorized processes. The OS enforces protection through mechanisms that separate policy (who can access what) from mechanism (how access is controlled).

Goals of Protection

  • Controlled AccessEnsure each resource is accessed only by processes authorized to use it.
  • Data IntegrityPrevent unauthorized modification of critical data and OS structures.
  • System ReliabilityProtect the system from accidental or malicious misuse by users or programs.
  • IsolationEnsure one process/user cannot interfere with another.

Principle of Least Privilege

💡 Core Principle
Programs, users, and systems should be given just enough privilege to perform their tasks — no more. This limits damage if an entity has a bug or is compromised.
  • Static: Fixed privileges for the entire life of the system or process.
  • Dynamic: Privileges change as needed (domain switching, privilege escalation).
  • Coarse-grained: Unix-style (user or root). Simple but less precise.
  • Fine-grained: ACLs, RBAC. More complex but more secure.

Domain of Protection

Access Right = <object-name, rights-set> where rights-set ⊆ all valid operations on that object.
Domain = a set of access rights. Can be a user, process, or procedure.

Access Matrix

Definition — Access Matrix A 2D matrix where rows = domains (subjects/users) and columns = objects (resources). Cell Access(i,j) = set of operations domain Dᵢ can invoke on object Oⱼ.

Security & Threats

Definition — Security A system is secure if its resources are used and accessed as intended under all circumstances. True security is theoretically unachievable; the goal is to make breaches sufficiently difficult and detectable. An attack is an attempt to breach security; a threat is a potential violation.

Security Violation Categories

Breach of Confidentiality

Unauthorized reading of data. E.g., intercepting private messages.

Breach of Integrity

Unauthorized modification of data. E.g., altering financial records.

Breach of Availability

Unauthorized destruction of data or services (DoS attacks).

Theft of Service

Unauthorized use of resources. E.g., crypto-mining via compromised servers.

Denial of Service (DoS)

Prevents legitimate use by flooding server with requests.

Security Attack Methods

Replay AttackCapturing valid authentication data and replaying it later (with or without modification)Replaying a login token
Man-in-the-MiddleIntruder sits between sender and receiver, masquerading as both sidesARP spoofing, SSL stripping
Session HijackingIntercepts an already established session to bypass authentication entirelyStealing session cookies
Denial of ServiceFloods resources to prevent legitimate useUDP flood, SYN flood, DDoS

Program Threats (Software-Level)

Trojan Horse

A program that appears useful or legitimate but secretly performs malicious actions in the background. Exploits user trust to execute harmful code.

e.g. game.exe → secretly logs keystrokes

Logic Bomb

Malicious code that is dormant until a specific condition or event triggers it (date, user action, system state). Difficult to detect before triggering.

if(date == "2024-01-01") delete_all()

Trapdoor / Backdoor

A secret undocumented entry point into a program, left by a developer for debugging or maliciously. Bypasses normal authentication.

Stack Overflow / Buffer Overflow

Writing data beyond the allocated buffer boundary on the stack. Overwrites return address to execute attacker's code. Classic exploitation technique.

char buf[8];          // only 8 bytes
strcpy(buf, input);   // no bounds check!
// If input > 8 bytes → overflow!

Virus

Self-replicating code that attaches to legitimate programs. Spreads when infected programs are executed. Requires human interaction to propagate.

Worm

Self-replicating program that spreads independently over networks without needing a host file. Famous example: Morris Internet Worm (1988).

The Morris Internet Worm (1988)

📌 Historic Case Study
Released by Robert Morris in 1988 — the first major Internet worm. Exploited three vulnerabilities: (1) sendmail debug — debug mode allowed remote command execution. (2) fingerd buffer overflow — used stack overflow to gain shell. (3) rsh/rexec trust — exploited trusted host relationships. The worm replicated so aggressively that it caused the first major Internet slowdown, infecting ~6,000 machines (10% of the Internet at the time).

Distributed Operating Systems & Networks

Definition — Distributed System A distributed system is a collection of loosely coupled processors interconnected by a communications network. Processors are called nodes/computers/machines/hosts; their physical location is called a site.

Reasons for Distributed Systems

Resource Sharing

Share files, printers, databases, and specialized hardware across remote sites.

Computation Speedup

Load sharing — distribute work across multiple processors for parallelism.

Reliability

Detect and recover from site failures; transfer functions to surviving nodes. Higher availability.

Communication

Message passing between geographically distributed sites.

Connection Strategies

Circuit Switching

A permanent physical link established for the duration of the entire communication session. Requires setup time. Less per-message overhead. May waste bandwidth when idle.

Example: Telephone system

Message Switching

A temporary link established for the duration of one message. Like mail — store-and-forward. No dedicated path. Messages may be large.

Example: Post-office mailing system

Packet Switching

Messages of variable length divided into fixed-length packets. Each packet may take a different path. Packets reassembled at destination. High overhead but efficient.

Example: Internet (TCP/IP)

Contention Resolution

CSMA/CD (Ethernet)

Before transmitting: sense the carrier (check if link is busy). If collision detected: stop, wait random time, retry. Used in Ethernet (IEEE 802.3). Degrades under heavy load.

A special token message circulates in a ring. A site must possess the token before transmitting. After transmission, the token is re-released. Deterministic — no collisions. Used in IBM Token Ring.

Synchronous Message Passing

Both sender and receiver must be synchronized. Sender blocks until receiver accepts the message. Analogous to a phone call — both parties must be active simultaneously.

Sender sends message and continues without waiting. Messages buffered until receiver reads them. Enables concurrent execution. Higher throughput. Like email — sender doesn't wait for reply.

5 Mark Questions — Detailed Answers (10–15 lines)

11
Compare RAID 0, RAID 1, RAID 5, and RAID 6 with respect to performance, fault tolerance, and storage efficiency.
5 marks
Answer
  • RAID 0 (Striping): Best read/write performance — data striped across all disks simultaneously. Zero fault tolerance — one disk failure = total data loss. Storage efficiency = 100% (no overhead). Used for temporary/performance-critical data.
  • RAID 1 (Mirroring): Excellent read performance (can read from either mirror); slower writes (must write to both). Tolerates 1 disk failure. Storage efficiency = 50% (half used for duplication). Used for OS drives and critical data.
  • RAID 5 (Distributed Parity): Good read performance; moderate write (parity must be recalculated). Tolerates exactly 1 disk failure. Storage efficiency = (n−1)/n. Parity is distributed across all disks (no parity disk bottleneck). Most popular RAID for file servers.
  • RAID 6 (Double Distributed Parity): Good read; slower writes (two parity calculations). Tolerates 2 simultaneous disk failures. Storage efficiency = (n−2)/n. Ideal for large-capacity arrays where rebuild time creates high risk of second failure. Best for high-availability enterprise systems.
Key insight: RAID 5 vs 6 trade-off is write performance vs. additional fault tolerance. As drive capacities grow, rebuild times lengthen, making RAID 6's double parity increasingly valuable.
12
Explain the three file allocation methods with their advantages and disadvantages.
5 marks
Answer
1. Contiguous Allocation: Each file occupies a set of adjacent disk blocks. Requires only start block and length. Pros: Best performance for sequential and random access; simple disk head movement. Cons: External fragmentation over time; must know file size in advance; compaction needed periodically (expensive).

2. Linked Allocation: Each file is a linked list of disk blocks scattered anywhere on disk; each block contains a pointer to the next. Pros: No external fragmentation; files can grow dynamically; simple free-space management. Cons: Only sequential access supported (must traverse chain to reach block n); pointer overhead in every block; reliability issues (one broken pointer = lost file tail). FAT is an optimized variation.

3. Indexed Allocation: Each file has a dedicated index block containing an array of pointers to all data blocks. Directory entry points to the index block. Pros: Supports both sequential and direct access; no external fragmentation; dynamic growth. Cons: Index block overhead (wastes space for small files); large files need multi-level or combined index schemes.

Summary: Contiguous = best performance but fragmentation; Linked = no fragmentation but poor random access; Indexed = best general-purpose solution used by most modern filesystems (Unix inodes use a combined index scheme).
13
Explain the layered architecture of a file system. What is the role of each layer?
5 marks
Answer
File system is organized in layers, each providing services to the layer above using services from the layer below:
  1. Application Programs: Top level; user programs make system calls for file operations (open, read, write).
  2. Logical File System: Manages metadata (file control blocks/inodes). Translates file name → file number → location. Handles directory management and protection.
  3. File-Organization Module: Understands logical and physical file blocks. Translates logical block numbers to physical block addresses. Manages free space and disk allocation.
  4. Basic File System: Manages memory buffers and caches. Buffers hold data in transit; caches hold frequently used data. Sends generic commands like "read block 123."
  5. I/O Control (Device Drivers): Translates high-level commands into low-level hardware-specific instructions for the disk controller (e.g., "read drive1, cylinder 72, track 2, sector 10").
  6. Physical Device: Actual disk hardware performing the I/O.
Layering reduces complexity and redundancy but adds overhead and may decrease performance. Each layer's boundaries can be implemented differently by different OS designers.
14
Describe the types of directory structures used in operating systems.
5 marks
Answer
1. Single-Level Directory: All files stored in one directory. Simple to implement. Problem: all file names must be globally unique; no organization for multi-user environments.

2. Two-Level Directory: One Master File Directory (MFD) at the top; each user gets their own User File Directory (UFD). Users are isolated — different users can have files with the same name in their own UFDs. Limitation: no sub-grouping within a user's directory.

3. Tree-Structured (Hierarchical) Directory: Most common structure. Each entry can be a file or a subdirectory, allowing unlimited nesting depth. Supports grouping of related files. Users have private directories. Paths can be absolute (from root: /home/user/file) or relative (from current directory: ./file). Only root/admin has full control of the root. Eliminates limitations of both prior structures. Used in all modern OS (Unix, Windows, macOS).

Implementation: Directories implemented as linear lists (simple but slow O(n) search) or hash tables (O(1) average but collision-prone) or B+ trees (O(log n), ordered). Modern filesystems like NTFS and ext4 use B-tree variants for directory lookup.

Explain free space management techniques in operating systems.
5 marks
Answer
The OS must track which disk blocks are free for allocation. Four main techniques:
  1. Bit Map (Bit Vector): One bit per block; 0=free, 1=used. Simple bitwise operations find contiguous free blocks efficiently. Requires extra space (proportional to total blocks). Example: 1 GB disk with 4KB blocks requires 32,768 bits = 4KB bitmap. Entire bitmap can be kept in memory for speed.
  2. Linked List: All free blocks linked together; first free block holds pointer to next free block. Simple but traversal is costly — finding n free blocks requires n disk reads. Not efficient for contiguous allocation requests.
  3. Grouping: A modification of linked list. The first free block stores addresses of the next n−1 free blocks plus a pointer to the next group block. Allows retrieving multiple free block addresses in one disk read — much more efficient than simple linked list.
  4. Counting: Stores pairs of (first free block address, count of contiguous free blocks following it). Very efficient when files are often allocated and freed as contiguous extents. Free list entries are compact.
Modern filesystems like ext4 use extent-based free space management (a form of counting), while Linux uses buddy system allocation for memory-mapped regions.

Explain the goals and principles of protection in operating systems.

Answer
Protection Goals: In a protection model, a computer consists of objects (hardware or software), each with a unique name and a defined set of operations. Protection ensures each object is accessed correctly and only by authorized processes. Goals include: controlled access to resources, data integrity (prevent unauthorized modification), system reliability, and process isolation.

  1. Physical Layer: Handles mechanical and electrical details of transmitting raw bits over the physical medium (cables, radio waves).
  2. Data Link Layer: Organizes bits into frames; handles error detection and recovery for point-to-point links.

Explain synchronous vs asynchronous message passing in distributed systems.
5 marks
Answer
In distributed systems, processes on different nodes communicate by exchanging messages through communication channels. Two fundamental models:

Synchronous Message Passing: Both sender and receiver must be synchronized at the moment of communication. The sender blocks (waits) until the receiver actively accepts the message. Communication fails if receiver never accepts. Analogous to a phone call — both parties must be active simultaneously. Simpler to reason about (no buffering needed) but reduces concurrency since sender is blocked.

Asynchronous Message Passing: The sender sends and immediately continues without waiting. Messages are buffered in communication channels until the receiver is ready to accept them. Analogous to email. Enables concurrent execution — sender and receiver operate independently. Higher throughput but requires message buffering infrastructure. Out-of-order delivery may be an issue.

Message Types by Scope: Unicast (1→1), Multicast (1→group), Broadcast (1→all nodes).

Communication is complete only when receiver accepts the message. In the message-passing model for distributed systems, channels are typically private between communicating processes, and successful communication requires active participation from both sides.

  • Data blocks are striped across all disks (like RAID 5).
  • Two independent parity values (P and Q, using Reed-Solomon codes) are calculated per stripe and stored on different disks.

  • Access(D2, F2) = {read, write}
  • Access(D3, F2) = {read, write, owner}
  • Access(D1, Printer) = {print}
  • Access(D2, Printer) = {print}
Implementation 1 — Global Table: List of triplets: (domain, object, rights). Every access check requires scanning the entire table. Large tables (many domains × many objects) are expensive. No natural grouping by domain or object. Rarely used in practice.

Implementation 2 — Access Control Lists (ACL): Each object maintains its own list of (domain, rights) pairs. Unix implements a simplified ACL as owner/group/other permission bits (rwx). Full ACLs (POSIX ACLs, Windows NTFS ACLs) allow per-user/group entries.

  • ✅ Easy to determine all resources a domain can access (just enumerate its capability list)
  • ✅ Fast access check (present capability → access granted)
  • ❌ Difficult to revoke access to a specific object (must find and destroy all capabilities for that object across all domains)
  • Used in: Hydra OS, some microkernel designs
Implementation 4 — Lock-Key Mechanism: Each object has a set of "locks" (bit patterns); each domain has a set of "keys." Access is granted when a domain's key matches an object's lock. Flexible but requires careful key management. Provides a middle ground between ACLs and capabilities.

}
Stack Layout Before Attack:
[buf (64 bytes)] [saved EBP (4 bytes)] [return address (4 bytes)] [arguments]
→ lower addresses ←→ higher addresses →

Attack Execution Steps:
  1. Attacker sends an input larger than 64 bytes (e.g., 200 bytes).
  2. strcpy() copies bytes into buf without checking size.
  3. After 64 bytes, the copy overflows into saved EBP, then continues into the return address.
  4. Attacker carefully crafts the input so bytes 69–72 (at the return address position) contain the address of attacker's shellcode.
  5. The shellcode (malicious instructions, e.g., execve("/bin/sh", null, null)) is embedded earlier in the input buffer or in an environment variable.
  6. When authenticate() returns, CPU loads the overwritten return address (attacker's address) instead of the legitimate return address.
  7. CPU jumps to attacker's shellcode and executes it — with the privileges of the vulnerable program.
  8. If the vulnerable program runs as root (SUID), attacker gets a root shell.
Stack Layout After Attack:
[NOP sled...shellcode...] [overwritten EBP] [attacker's shellcode address] [args]

NOP Sled Technique: Attacker doesn't know exact address of shellcode, so prepends many NOP instructions (no-operation, 0x90). CPU slides through NOPs until it hits shellcode. Increases attack reliability.

OS-Level Defenses:
  1. Stack Canaries: Compiler (gcc -fstack-protector) places a random "canary" value between buffer and return address. Before function returns, canary is checked — if modified, execution is aborted. Detects overflow before control is transferred.
  2. ASLR (Address Space Layout Randomization): OS randomizes base addresses of stack, heap, and libraries on each execution. Attacker cannot reliably predict address to jump to. Effective against hardcoded address attacks.
  3. NX/DEP (Non-Executable Stack/Data Execution Prevention): Memory regions marked as data (stack, heap) are flagged as non-executable (NX bit in page table). CPU refuses to execute instructions from these regions — shellcode on stack cannot run.
  4. Safe Functions: Use strncpy(buf, input, 63) instead of strcpy(); use fgets() instead of gets(). Modern C compilers warn about unsafe functions.
  5. Bounds Checking: Use safe languages (Rust, Java) or static analysis tools (Coverity, CodeQL) to detect buffer overflows before deployment.
  6. Control Flow Integrity (CFI): Modern GCC/LLVM insert runtime checks ensuring function return addresses match expected valid locations — prevents arbitrary code execution even if return address is overwritten.
  7. Principle of Least Privilege: Run servers as non-root users; even successful exploitation gives limited privilege rather than root access.
Conclusion: Buffer overflow attacks exploit the combination of unsafe string functions, contiguous stack layout, and CPU's blind trust in return addresses. Modern defense is layered: stack canaries (detect), ASLR (complicate), NX (prevent execution), bounds-safe code (eliminate vulnerability at source). No single defense is complete; all should be deployed simultaneously.

Compare P2P and Client-Server models for building a distributed file storage system handling 100TB of data across 1000 nodes. Analyze failure scenarios, performance, consistency, and security for both models. Which would you recommend and why?
10 marks
Answer
System Parameters: 100TB data, 1000 storage nodes, global distribution, multiple concurrent users, high availability requirement.

Client-Server Architecture Analysis:
One or few central metadata servers; data servers store chunks; clients communicate with metadata server for file locations, then with data servers for actual data.
  • Performance: Metadata server is bottleneck — all namespace operations (list, create, delete) funnel through it. With 1000 nodes, if metadata server handles 10,000 operations/second, it limits overall system throughput. Data transfer goes directly to data servers (fast). Vertical scaling of metadata server expensive.
  • Consistency: Strong consistency easy — metadata server is the single authority. All clients always see latest file list. Suitable for financial/medical data.
  • Failure Scenario: Metadata server failure = entire system inaccessible (SPOF). With replication (primary-secondary): 30-60 second failover window — unacceptable for high-availability needs. 1000 data nodes: statistically, one fails every ~15 days at 0.5% AFR → handled by replication.
  • Security: Centralized control makes access control straightforward. Single point to enforce authentication, authorization, encryption. Audit logging centralized. However, metadata server compromise = full system compromise.
  • DDoS Vulnerability: Metadata server is a target — concentrated attack can take down entire system.
  • Examples: GFS (Google File System), HDFS — use a single NameNode (client-server for metadata) + distributed DataNodes (P2P for data). Google found 1 NameNode sufficient for petabytes.
Peer-to-Peer Architecture Analysis:
All nodes are equal; no central authority. Using consistent hashing (like Amazon Dynamo, Chord protocol), each node is responsible for a portion of the key space.
  • Performance: No central bottleneck — reads/writes distributed across all 1000 nodes simultaneously. Scales linearly: adding nodes increases total throughput proportionally. Excellent for high-volume parallel access.
  • Consistency: Hard to maintain strong consistency — updates must propagate to all replicas. Most P2P systems use eventual consistency (Dynamo, Cassandra): nodes may temporarily serve stale data. Unsuitable for strict financial/medical applications without modifications.
  • Failure Scenario: Highly resilient — no SPOF. Node failure only affects its data; other nodes reconstruct the data using redundant copies. System continues fully operational. 1000 nodes: even 10% simultaneous failures = 900 nodes still operational. DHT (Distributed Hash Table) automatically redistributes responsibility for failed nodes' data.
  • Security: Harder to secure — no central authority to enforce policies. Sybil attacks (attacker creates many fake nodes) can compromise data availability. Requires cryptographic proof-of-identity. Each node must verify all received data — Byzantine fault tolerance is complex.
  • Examples: BitTorrent, IPFS, Amazon Dynamo, Apache Cassandra.
Recommendation for 100TB / 1000 Nodes:
Hybrid Architecture: Client-Server for metadata, P2P for data (GFS/HDFS model)
  • Metadata (namespace, file locations) on replicated client-server nodes (primary + 2 secondaries for high availability).
  • Data blocks stored P2P across all 1000 nodes — each block replicated 3× on nodes in different racks/zones.
  • This gives: Strong consistency for namespace operations; High throughput for data access (parallel across 1000 nodes); No SPOF (data servers) + fast metadata failover; Manageable security (central auth server).

This is exactly the architecture of Google File System, Amazon S3 (with metadata databases + S3 object storage nodes), and HDFS — proven at 100TB+ and billion-file scale in production. Pure P2P introduces consistency complexity; pure client-server creates bottlenecks at 1000+ nodes. The hybrid captures the best of both.

A financial firm runs a multi-user OS with strict security requirements. Design a complete protection and security architecture using the Principle of Least Privilege, Access Matrix, and protection against all known program threats (Trojan, virus, worm, logic bomb, buffer overflow). Show implementation with pseudocode where appropriate.
10 marks
Answer
Security Architecture Design for Financial OS:

1. Domain-Based Protection Model (Principle of Least Privilege):
Define minimum-privilege domains for each role: 
Domains:
  D_trader  = { read: market_data, write: trade_orders }
  D_analyst = { read: market_data, read: trade_reports }
  D_admin   = { read: all, write: system_config, NOT write: trade_orders }
  D_auditor = { read: all_logs, NOT write: anything }
  D_process = { execute: specific_binary, NOT network: external }

Objects:
  market_data (file), trade_orders (file), system_config (file)
  trade_reports (file), all_logs (file), network (device)
  printer (device), database (service)
2. Access Matrix Implementation: 
Access Matrix:
              market_data  trade_orders  system_config  logs    network
D_trader      [read]       [read,write]  []             [read]  [trade_API only]
D_analyst     [read]       [read]        []             [read]  [read_only]
D_admin       [read,write] []            [read,write]   [read]  [admin_API]
D_auditor     [read]       [read]        []             [read]  []
D_process     []           [execute]     []             [write] []

Implementation: ACL per object + Capability tokens per session
3. Protecting Against Program Threats:

Against Trojan Horse:
  • Code signing: all executables must be signed with company's certificate. OS refuses to run unsigned binaries.
  • Whitelist-only execution: only approved binaries may run — no ad-hoc program execution by users.
  • Application sandbox: each program runs in a restricted domain with no access to other programs' data.
  • User education: training on phishing and social engineering (most trojans enter via user action).
Against Virus:
  • Read-only file system for all executables: programs stored on read-only partition → virus cannot modify them.
  • Real-time antivirus scanning with behavioral detection (not just signature-based).
  • Integrity monitoring: cryptographic hashes of all executables checked daily (SHA-256 hash database).
Against Worm:
  • Network segmentation: trading systems on isolated VLAN, no direct Internet access.
  • Strict firewall rules: default-deny inbound and outbound; whitelist specific services only.
  • Rate limiting on network connections: abnormal connection volume triggers alert + automatic quarantine.
  • Patch management: all systems patched within 24 hours of critical security update release — eliminates worm entry points.
Against Logic Bomb: 
// Static code analysis tool scans all commits
function scan_for_logic_bombs(source_code):
    patterns = [
        /if.*date.*==.*delete/i,      // date-triggered deletion
        /if.*user.*==.*"fired"/i,      // condition-triggered action
        /sleep.*86400.*rm -rf/i,       // delayed destructive command
    ]
    for pattern in patterns:
        if pattern.match(source_code):
            flag_for_manual_review()
            block_commit()
Additional: mandatory code review by two developers; no single person can approve their own commits; audit logging of all code deployments.

Against Buffer Overflow: 
// All code compiled with protections enabled:
gcc -o trading_app trading.c \
    -fstack-protector-all \    // stack canaries
    -D_FORTIFY_SOURCE=2 \      // safe library functions
    -pie -fPIE                 // position-independent (aids ASLR)

// OS Configuration:
sysctl -w kernel.randomize_va_space=2   // full ASLR
echo 1 > /proc/sys/kernel.exec-shield   // NX bit enabled
4. Runtime Monitoring:
  • System call auditing (auditd): log all privilege escalations, file accesses, network connections.
  • SIEM (Security Information and Event Management): correlate events across all systems — detect anomalies in real-time.
  • Canary accounts: fake user accounts that should never be logged into — any login attempt triggers immediate security alert.
  • Network traffic analysis: baseline normal trading traffic patterns; alert on deviations (potential exfiltration or worm spreading).
5. Incident Response Protocol: 
Detection → Isolation → Analysis → Eradication → Recovery → Lessons

Detection:   IDS/SIEM alert, FIM alert, or user report
Isolation:   Automatically quarantine affected system (block network)
Analysis:    Forensic memory/disk capture before any cleanup
Eradication: Remove malware, patch vulnerability, reset credentials
Recovery:    Restore from clean backup, verify integrity
Lessons:     Update policies, detection rules, training
Conclusion: A comprehensive financial OS security architecture layers defenses at every level: domain-based access control (Principle of Least Privilege + Access Matrix) for authorization; code signing and whitelisting against trojans; read-only executables + FIM against viruses; network segmentation + firewalling against worms; static analysis + code review against logic bombs; stack canaries + ASLR + NX against buffer overflows; plus continuous monitoring and incident response. No single measure suffices — the depth of layering determines overall security strength.
