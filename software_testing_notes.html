01 Introduction to Software Testing

Foundations, objectives, and Glen Myers' principles — exam mein almost har baar aata hai!

📘 Definition

Software Testing is the process of verifying and validating that a software application is bug-free, meets technical requirements as guided by its design and development, and meets user requirements effectively and efficiently while handling all exceptional and boundary cases.

🎯 Glen Myers — Testing Objectives

According to Glen Myers, software testing is a process of investigating a program to find errors. Key points:

  • Finding an unknown error not yet discovered = sign of a good test case
  • Higher number of errors found = better quality of testing
  • Goal: find different types of errors without taking much time
🧠 Mnemonic

VERI-VALI-FIND — Verify (right build?), Validate (right product?), Find bugs early!

🔑 Key Testing Principles (from PPT Slide 5)

1. Testing Shows Presence — Not Absence

Testing can reveal bugs but cannot prove software is 100% bug-free.

2. Exhaustive Testing is Impossible

Can't test every input/path combination. Prioritize critical areas.

3. Early Testing

Defects are cheaper to fix earlier in SDLC. "Shift Left" testing.

4. Defect Clustering (Pareto Principle)

80% defects found in 20% of modules — focus testing on these.

5. Pesticide Paradox

If same test cases run repeatedly, they stop finding new bugs. Update test cases regularly!

⚠️
Exam Alert: "Pesticide Paradox" is a frequently asked MCQ/short answer. Remember: running same tests = missing new bugs. Test cases must evolve!

02 Verification vs Validation

The most classic distinction in SE exams — "Right product vs Product right!"

✅ Verification — "Are we building the product RIGHT?"

A set of tasks that ensure software correctly implements a specific function. Checks conformance to specifications. It is a static testing approach — involves reviews, inspections, walkthroughs.

🎯 Validation — "Are we building the RIGHT product?"

A set of tasks that ensure the software built is traceable to customer requirements. It is a dynamic testing approach — involves actual execution. Done AFTER verification.

03 Software Testing Strategy

Ek overall plan — what, how, when, and who to test. Very important for 5-mark answers!

📘 Definition

A Software Testing Strategy is a high-level plan that defines the testing scope, objectives, resources, and timelines. It aligns with the SDLC methodology and ensures systematic, organized testing throughout development.

📋 Key Strategy Components (8 Points)

  • 1
    Identify and specify requirements quantifiably — maintainability, probability, usability should be measurable.
  • 2
    Specify testing objectives clearly — effectiveness, failure handling, cost of defects.
  • 3
    Identify user categories — develop profiles for each user type (use cases).
  • 4
    Develop a test plan — enable rapid-cycle testing for continuous quality improvement.
  • 5
    Robust self-testing software — design software that can detect different error classes automatically.
  • 6
    Use formal reviews as filters before testing — reduces testing effort and time significantly.
  • 7
    Conduct formal technical reviews — evaluate quality of test strategy and test cases.
  • 8
    Continuous improvement approach — statistical process control for measuring and controlling quality.

🔄 Rapid Cycle Testing

A type of testing that improves quality by identifying and measuring changes needed to improve the software process. A test plan is an essential document for enabling this.

💡
Rapid Cycle Testing = jaldi jaldi small cycles mein test karo, improvements laate raho continuously. Like Agile sprints!

05 Validation Testing

Customer satisfaction confirm karna — "Right product banaya kya?"

📘 Definition

Validation Testing is the process of evaluating software during or at the end of development to determine whether it satisfies specified business requirements. It ensures the product actually meets the client's needs and demonstrates fulfillment of its intended use when deployed in the appropriate environment.

📋 Stages of Validation Testing Process

  • 1
    Validation Planning — Plan all activities to be included
  • 2
    Define Requirements — Set goals and define testing requirements
  • 3
    Selecting a Team — Skilled development/QA team (third party included)
  • 4
    Developing Documents — User specification document with operating conditions
  • 5
    Estimation/Evaluation — Evaluate as per specs, submit validation report
  • 6
    Fixing Bugs / Incorporating Changes — Remove errors found during evaluation

🔀 Validation Testing Variations

Unit Testing

Looks for bugs in individual components. Tests modules/objects separately.

Integration Testing

Tests interaction between different interfaces of components AND interaction with OS, hardware, file system.

System Testing

Entire software system is ready. Verifies system against specified requirements.

Acceptance Testing

Tester thinks like a CLIENT — checks user needs, business processes.

Alpha Testing

At developer site with potential customers. Problems fixed immediately.

Beta Testing

After alpha — conducted at user's end in real environment.

Regression Testing

After changes/modifications are made to existing code — ensures new code still fulfills customer requirements without introducing new bugs.

06 Black Box Testing

Internal code nahi pata — sirf inputs/outputs se test karo. Behavioral Testing bhi kehte hain!

📘 Definition

Black Box Testing (aka Behavioral Testing) is a software testing method in which functionalities of software are tested without having knowledge of internal code structure, implementation details, and internal paths. It focuses entirely on input and output, based on software requirements and specifications.

⬛ How to Perform Black Box Testing — Steps

  • 1
    Examine requirements and specifications of the system
  • 2
    Choose valid inputs (positive scenario) and invalid inputs (negative scenario)
  • 3
    Determine expected outputs for all inputs
  • 4
    Construct test cases with selected inputs
  • 5
    Execute the test cases
  • 6
    Compare actual outputs with expected outputs
  • 7
    Fix defects and re-test

🔧 Black Box Testing Techniques — Detailed

1. Equivalence Partitioning (EP)

Partition the input domain into equivalence classes where each member of a class behaves similarly. If one test case in a class fails, all others in that class also fail.

Two steps: (a) Identify equivalence classes — valid & invalid. (b) Generate test cases covering all classes.

📐 Worked Example — Square Root Function

Valid Classes:

  • Whole number, perfect square → integer output (e.g., 9 → 3)
  • Whole number, not perfect square → decimal output (e.g., 7 → 2.64...)
  • Positive decimals (e.g., 2.5)

Invalid Classes:

  • Negative numbers (integer or decimal) — e.g., -4
  • Non-numeric characters — e.g., "a", "!", ";"

Instead of testing ALL possible inputs, we test ONE representative from each class — fewer test cases, same effectiveness!

2. Boundary Value Analysis (BVA)

Errors tend to cluster at boundaries of input domains. BVA tests values at, just below, and just above boundaries.

📐 Example — Valid Range: 10 to 100

Test these values: 9 (just below), 10 (boundary), 11 (just above), 50 (mid-valid), 99, 100 (boundary), 101 (just above invalid)

High defect detection rate with limited test cases!

3. Cause-Effect Graphing

Establishes relationships between logical inputs (causes) and corresponding actions (effects) using Boolean graphs, then converts to a decision table.

  • 1
    Identify inputs (causes) and outputs (effects)
  • 2
    Develop cause-effect graph
  • 3
    Transform graph into decision table
  • 4
    Convert decision table rules into test cases
⚠️
Each column in the decision table = 1 test case. If there are 2 conditions, there are 2² = 4 test cases minimum.

4. Syntax Driven Testing

Applied to systems that can be represented syntactically by a language (e.g., compilers, context-free grammars). Test cases ensure each grammar rule is used at least once.

5. Requirement Based Testing

Validates the requirements given in the SRS (Software Requirements Specification) of the system.

6. Compatibility Testing

Tests software across different infrastructure parameters: Processor type, OS (Windows/Linux), Architecture (32-bit/64-bit), Backend components (database servers).

Equivalence PartitioningReduce number of test casesFewer test cases neededMisses complex boundary flaws

Cause-Effect GraphingModel condition-outcome logicDetailed logic coverageComplex to create

07 White Box Testing

Code dekhke test karo — Glass Box, Clear Box, Structural Testing bhi bolte hain!

📘 Definition

White Box Testing (also called Clear Box / Glass Box / Structural / Code-based Testing) is a software testing technique in which internal structure, design, and code are tested to verify the flow of input-output and improve design, usability, and security. Testers have full access to source code.

⬜ What White Box Testing Verifies

  • Internal security holes
  • Broken/poorly structured code paths
  • Flow of specific inputs through code
  • Expected output correctness
  • Functionality of conditional loops
  • Each statement, object, and function individually
💡
White Box Testing requires the tester to have programming knowledge. Testers must carefully reason about the implementation details.

🔬 White Box Testing Techniques — Detailed

1. Statement Coverage

Every executable statement in the program must be executed at least once. In a flowchart, every node must be traversed at least once. Simple but lowest level of coverage.

// Formula Statement Coverage = (Executed Statements / Total Statements) × 100%

2. Branch Coverage (Decision Coverage)

Every branch from every decision point must be executed at least once — both TRUE and FALSE branches. In a flowchart, all edges must be traversed at least once.

📐 Example

For a program with 2 decision points (if/else branches): minimum 4 test cases required (True-True, True-False, False-True, False-False)

3. Condition Coverage

All individual Boolean conditions must evaluate to both TRUE and FALSE at least once.

📐 Example

Code: IF (X == 0 || Y == 0)

Two conditions: X==0, Y==0

  • TC1: X=0, Y=55 → X==0 is TRUE, Y==0 is FALSE
  • TC2: X=5, Y=0 → X==0 is FALSE, Y==0 is TRUE

4. Multiple Condition Coverage

All possible combinations of condition outcomes tested at least once. For n conditions → 2ⁿ test cases required.

📐 Example — 2 Conditions → 4 Test Cases

Code: IF (X == 0 || Y == 0)

  • TC1: X=0, Y=0 (T, T)
  • TC2: X=0, Y=5 (T, F)
  • TC3: X=55, Y=0 (F, T)
  • TC4: X=55, Y=5 (F, F)

General rule: n conditions → 2ⁿ test cases

5. Loop Testing

Loops are fundamental to algorithms, so they need special testing. Errors often occur at the beginning and end of loops.

Simple Loops (size n):

  • Skip the loop entirely
  • Only 1 pass through loop
  • 2 passes
  • m passes (where m < n)
  • n-1 passes
  • n+1 passes

Nested Loops:

  • Start from innermost loop
  • Set all outer loops to minimum count
  • Run simple loop tests on innermost
  • Work outward until all loops tested

Concatenated Loops:

  • Independent → apply simple loop tests to each
  • Not independent → treat like nesting

08 Basis Path Testing & Cyclomatic Complexity

Most important numerical topic! Cyclomatic complexity formula ko perfectly yaad karo!

📘 Definition

Basis Path Testing is a White Box testing technique that uses the control structure of a program to derive test cases. A control flow graph is prepared and all possible paths present in the graph are executed. It ensures 100% statement coverage AND 100% branch coverage.

📊 Control Flow Graph (CFG)

A Control Flow Graph (V, E) is a directed graph representing the control structure of a program/module.

Node Types:

  • Junction Node: more than one arrow entering
  • Decision Node (Predicate Node): more than one arrow leaving
  • Region: area bounded by edges and nodes

Common Notations:

  • Sequential Statements → single flow
  • If-Then-Else → branching
  • Do-While / While-Do → loops
  • Switch-Case → multiple branches
Sample CFG Flow:
Node 1
↓
Node 2 [Decision]
↙      ↘
Node 3     Node 4
↘      ↙
Node 5 [Junction]
↓
Node 6 (End)

🔢 Cyclomatic Complexity V(G)

Cyclomatic Complexity is a measure of the logical complexity of a program. It defines the number of independent paths (minimum test cases needed).

// THREE EQUIVALENT FORMULAS — all give the same answer Formula 1 (Edges & Nodes): V(G) = E - N + 2P where E = edges, N = nodes, P = connected components (usually 1) Formula 2 (Decision Nodes): V(G) = d + P where d = number of decision/predicate nodes, P = connected components Formula 3 (Regions): V(G) = Number of regions in the flow graph // Include the outer region (outside the graph)
⚠️
Exam Critical: All three formulas MUST give the same answer. Use all three to verify in numericals! If they don't match, you made an error somewhere.

Cyclomatic Complexity Risk Interpretation (from PPT Slide 24):

V(G) RangeRisk LevelInterpretation
V(G) ≤ 10🟢 Low RiskSimple program, easy to test
V(G) = 11–20🟡 Moderate RiskModerate complexity, manageable
V(G) = 21–50🔴 High RiskComplex program, difficult to test
V(G) > 50⛔ Very High RiskEssentially untestable — refactor!

📐 Worked Numerical — Basis Path Testing

📐 Complete Solved Example

Given Flow Graph: Consider a graph with the following structure:

  • Nodes: 1, 2, 3, 4, 5, 6, 7, 8 (N = 8)
  • Edges: 1→2, 2→3, 2→4, 3→5, 3→6, 4→7, 5→7, 6→7, 7→8, 7→1 (E = 10 — wait, let's use the textbook example)

Standard Textbook Example (from Lecture 4):

A flow graph has 4 independent paths identified as:

  • P1: 1 → 2 → 4 → 7 → 8
  • P2: 1 → 2 → 3 → 5 → 7 → 8
  • P3: 1 → 2 → 3 → 6 → 7 → 8
  • P4: 1 → 2 → 4 → 7 → 1 → ... → 7 → 8 (loop path)

Calculation:

  • V(G) using Formula 1: E - N + 2 = (calculated from graph)
  • V(G) using Formula 2: P (predicate nodes) + 1
  • V(G) = 4 (all formulas agree)
  • Therefore, 4 independent paths, minimum 4 test cases needed
📐 Lecture 5 Example — Complete Walkthrough

Flow Graph from Lecture 5 (4 Paths):

  • Path 1: 1 → 2 → 5 → 7
  • Path 2: 1 → 2 → 5 → 6 → 7
  • Path 3: 1 → 2 → 3 → 2 → 5 → 6 → 7
  • Path 4: 1 → 2 → 3 → 4 → 2 → 5 → 6 → 7

→ V(G) = 4 → 4 independent paths → design 4 test cases

✅ Steps for Basis Path Testing

  • 1
    Draw/Construct the Control Flow Graph from code or flowchart
  • 2
    Compute Cyclomatic Complexity V(G) using any of 3 formulas
  • 3
    Identify Independent Paths — number equals V(G)
  • 4
    Design Test Cases corresponding to each independent path
💡
Independent Path: A path that introduces at least one new edge that has not been traversed before. The cyclomatic complexity = upper bound for number of tests needed.

🎯 Advantages of Basis Path Testing

More Coverage

Maximum logic coverage (not just path coverage) → thorough testing.

Maintenance Testing

When software is modified, basis path testing ensures changes are tested properly.

Unit Testing

Developers use it to test their own code structure before submitting.

Integration Testing

Tests all paths on module interfaces to avoid interface errors.

Testing Effort

Testing effort ∝ Cyclomatic complexity (more complex = more tests).

EASY 2 Mark Questions 3–4 lines · Q 1–10
Q1

Define Software Testing. What is its main objective?

Software Testing is the process of verifying and validating that a software application is bug-free, meets technical requirements, and satisfies user needs effectively while handling all exceptional and boundary cases.

The main objective is to systematically find different types of errors without consuming excessive time, so that the overall software development cost and time are reduced, and software quality is improved.

Q2

Differentiate between Verification and Validation. (2 marks)

Verification ("Are we building the product RIGHT?") ensures software correctly implements a specific function. It is a static process involving reviews, inspections, and walkthroughs — done during development.

Validation ("Are we building the RIGHT product?") ensures the built software is traceable to customer requirements. It is a dynamic process involving actual test execution — done after verification.

Q3

What is the Pesticide Paradox in software testing?

The Pesticide Paradox is a testing principle which states that if the same set of test cases is run repeatedly over time, they will eventually stop finding new defects — just like pests developing resistance to pesticides.

Solution: Test cases must be regularly reviewed and updated to discover new bugs. New and different test cases must be written to exercise different parts of the software to potentially find more defects.

Q4

What is Alpha Testing? How does it differ from Beta Testing?

Alpha Testing is performed at the developer's site in a controlled environment by internal testers/QA teams. It uses both White Box and Black Box techniques to find critical bugs early.

Beta Testing is conducted at the end user's site in real-world, uncontrolled conditions. Real users provide feedback on usability, performance, and compatibility. Beta follows alpha in sequence — alpha is internal, beta is external.

Q5

What is Black Box Testing? Give another name for it.

Black Box Testing (also called Behavioral Testing) is a software testing method where functionalities are tested without any knowledge of the internal code structure, implementation details, or internal paths. Testers focus only on inputs and outputs based on requirements and specifications.

It is well-suited for testing large code segments and is performed by an independent testing team.

Q6

What is White Box Testing? List any two other names for it.

White Box Testing is a software testing technique in which the internal structure, design, and code of software are tested to verify the flow of input-output and improve design, usability, and security. Testers have full access to the source code.

Other names: Glass Box Testing, Clear Box Testing, Structural Testing, Open Box Testing, Code-based Testing. It requires testers to have programming knowledge.

Q7

What is Cyclomatic Complexity? State the formula to calculate it.

Cyclomatic Complexity V(G) is a measure of the logical complexity of a program. It determines the number of independent paths in a control flow graph, which in turn gives the minimum number of test cases required.

Formulas:
(1) V(G) = E – N + 2P (E = edges, N = nodes, P = connected components)
(2) V(G) = d + P (d = decision nodes, P = components)
(3) V(G) = Number of regions in the flow graph

Q8

What is Regression Testing? When is it performed?

Regression Testing is a type of software testing performed after changes, modifications, or upgrades are made to existing code. Its purpose is to verify that the new changes have not broken or adversely affected any existing functionality.

It is performed after bug fixes, code changes, or new feature additions. It is also used in automation testing scenarios for repeated, efficient verification of unchanged functions.

Q9

What is the Defect Clustering principle in software testing?

Defect Clustering is a testing principle based on the Pareto Principle (80/20 rule). It states that approximately 80% of defects are found in about 20% of the software modules.

This principle guides testers to focus their testing efforts on these high-defect-density modules, leading to more efficient and effective defect discovery. Critical/complex modules get proportionally more testing attention.

Q10

What is IV&V (Independent Validation and Verification)?

IV&V (Independent Validation and Verification) refers to validation testing performed by a third-party organization rather than the development team. The developer provides a user manual describing the standard operating conditions.

The third-party organization conducts tests and submits a validation report to the developer. The developer then makes required changes and re-tests to confirm customer needs are met. IV&V provides an unbiased quality evaluation.

MEDIUM 5 Mark Questions 10–15 lines · Q 11–22
Q11

Explain the different levels of software testing with their objectives.

Software testing is performed at four major levels:

  • Unit Testing: Tests individual components/modules in isolation. Performed by developers in the early phase. Validates that each unit performs as designed. Detects bugs in individual functions/methods.
  • Integration Testing: Tests how units work together when combined. Performed by testers after unit testing. Focuses on interfaces and interactions between modules. Detects faults that arise from module integration.
  • System Testing: Tests the complete integrated system against specified requirements. A Black Box technique performed by the testing team. Evaluates both functional and non-functional requirements. Performed after integration testing and before acceptance testing.
  • Acceptance Testing: Tests whether the system meets business requirements and user expectations. Performed by the customer before final deployment. Determines if the software is acceptable for delivery. Includes Alpha Testing (internal) and Beta Testing (external users).
  • Regression Testing: Performed after any changes/fixes are made. Ensures new changes don't break existing functionality. Critical for maintaining software quality in iterative development.

The sequence is: Unit → Integration → System → Acceptance. Each level builds on the previous, progressively increasing the scope of testing from individual components to the complete system.

Q12

Explain Equivalence Partitioning with a suitable example.

Equivalence Partitioning is a Black Box testing technique where the input domain is divided into groups (equivalence classes) where all values in a class behave similarly. Instead of testing every possible input, one representative value from each class is tested.

Two steps:

  • Step 1 — Identify Equivalence Classes: Partition the input domain into valid and invalid value sets.
  • Step 2 — Generate Test Cases: Assign unique IDs to each class and write test cases covering all valid and invalid classes.

Example — Square Root Function:

Valid Classes:

  • EC1: Perfect square whole number (e.g., 9) → integer output
  • EC2: Non-perfect square whole number (e.g., 7) → decimal output
  • EC3: Positive decimal (e.g., 2.5)

Invalid Classes:

  • EC4: Negative numbers (e.g., -5)
  • EC5: Non-numeric characters (e.g., "a", "!")

Instead of testing thousands of numbers, we test one from each of 5 classes = only 5 test cases. This dramatically reduces testing effort while maintaining thoroughness.

Q13

Explain Boundary Value Analysis. How does it differ from Equivalence Partitioning?

Boundary Value Analysis (BVA) is a Black Box testing technique based on the observation that errors tend to cluster at the boundaries of input domains. By testing values at, just above, and just below the boundaries, the probability of finding errors increases significantly.

Boundary Values to test for a range [min, max]:

  • min - 1 (just below minimum — invalid)
  • min (boundary — valid)
  • min + 1 (just above minimum — valid)
  • Nominal/middle value (valid)
  • max - 1 (just below maximum — valid)
  • max (boundary — valid)
  • max + 1 (just above maximum — invalid)

Example: For valid range 10 to 100:
Test: 9, 10, 11, 55, 99, 100, 101

Difference from Equivalence Partitioning:

  • EP tests any representative value from a class (typically mid-range)
  • BVA specifically focuses on edge/boundary values where errors are most likely
  • BVA is complementary to EP — both are often used together
  • BVA has a higher defect detection rate for input validation errors
Q14

Explain the working process and advantages of White Box Testing.

White Box Testing tests the internal structure, design, and code of software. The tester has full access to source code and verifies internal security holes, code paths, loop functionality, and individual statement/function behavior.

Working Process:

  • Input: Requirements, functional specs, design documents, source code
  • Processing: Perform risk analysis, design test cases to cover entire code
  • Proper Test Planning: Execute tests, iterate until error-free; communicate results
  • Output: Prepare final report of the entire testing process

Advantages:

  • Very thorough — entire code and structures are tested
  • Optimizes code by removing extra lines and errors
  • Can start early — doesn't need an interface unlike Black Box
  • Easy to automate using coverage tools
  • Helps identify hidden security vulnerabilities in code

Disadvantages:

  • Very expensive — requires skilled programmers
  • Missing functionalities cannot be detected (tests only what exists)
  • Code redesign requires completely new test cases
  • Very complex and sometimes not practically achievable
Q15

Describe the different types of System Testing.

System Testing is a Black Box testing technique performed on the complete integrated system to evaluate compliance with requirements. It has several types:

  • Functional Testing: Verifies the system behaves according to functional requirements and specifications. Tests what the system does.
  • Performance Testing: Assesses speed, responsiveness, scalability, stability, and reliability of the software under different conditions. Tests how fast the system responds.
  • Load Testing: Tests system behavior under extreme or peak load conditions. Determines if the system can handle heavy user traffic.
  • Stress Testing: Tests robustness of the system under varying loads — often beyond normal capacity. Checks what happens when the system breaks.
  • Scalability Testing: Checks the system's ability to scale up or down in terms of user load. Important for cloud-based applications.
  • Security Testing: Evaluates the software's ability to protect against threats and vulnerabilities, including unauthorized access and data breaches.
  • Usability Testing: Measures how easy and intuitive the software is for end users — user experience focus.
  • Compatibility Testing: Verifies the software works correctly across different platforms, devices, browsers, OS, and hardware configurations.

System testing is performed AFTER integration testing and BEFORE acceptance testing. An independent testing team (not the development team) typically conducts it to ensure unbiased evaluation.

Q16

Explain Statement Coverage and Branch Coverage with examples.

These are two key White Box testing coverage techniques:

Statement Coverage: Ensures that every executable statement in the program is executed at least once. In a flowchart, every node must be traversed.

  • Formula: Statement Coverage = (Executed Statements / Total Statements) × 100%
  • It is the simplest and lowest level of coverage criterion
  • Example: A function with 10 statements — if 8 are executed during testing, coverage = 80%
  • Weakness: Doesn't guarantee both sides of a condition are tested

Branch Coverage (Decision Coverage): Ensures that every branch from every decision point (both TRUE and FALSE outcomes) is executed at least once.

  • In a flowchart, all edges must be traversed at least once
  • Example: for if (x > 0) { A() } else { B() }, both the TRUE branch (A executed) and FALSE branch (B executed) must be tested
  • Stronger than statement coverage — catches errors in conditional logic
  • Weakness: Misses combinations of conditions

Hierarchy: Path Coverage > Branch Coverage > Statement Coverage (in terms of thoroughness). Higher coverage = more test cases needed.

Q17

What is Cause-Effect Graphing? Explain the steps involved.

Cause-Effect Graphing is a Black Box testing technique that establishes relationships between logical inputs (causes) and corresponding actions/outputs (effects) using Boolean graphs. It helps in designing systematic test cases for complex conditions.

Steps:

  • Step 1 — Identify Causes and Effects: List all inputs (causes) and outputs/actions (effects) from the requirements/specifications
  • Step 2 — Develop Cause-Effect Graph: Represent causes and effects as nodes; connect them with Boolean relationships (AND, OR, NOT)
  • Step 3 — Transform into Decision Table: Convert the graph into a decision table where columns represent rules and rows represent causes/effects. Each column = one rule.
  • Step 4 — Convert to Test Cases: Each column (rule) in the decision table becomes one test case

Important Rule: If there are 2 conditions (causes), there will be 2² = 4 columns = 4 test cases minimum. For n conditions, 2ⁿ combinations exist.

Advantage: Systematically generates test cases that cover all combinations of input conditions, ensuring complete logical coverage of business rules. Especially useful for systems with complex interdependent conditions.

Explain the stages of Validation Testing Process.

Validation Testing is performed to ensure the software meets customer requirements. It involves the following stages:

  • Stage 1 — Validation Planning: Plan all activities that need to be included during testing. Define the scope, schedule, and approach for validation.
  • Stage 2 — Define Requirements: Set testing goals and clearly define the requirements. This becomes the baseline against which the software is evaluated.
  • Stage 3 — Selecting a Team: Select a skilled and knowledgeable development/QA team. Third-party validators (IV&V) may also be included for independent assessment.
  • Stage 4 — Developing Documents: Create a user specification document describing the operating conditions, environment, and expected behaviors of the software.
  • Stage 5 — Estimation/Evaluation: Evaluate the software against its specifications. Run tests and compile results into a validation report highlighting pass/fail status.
  • Stage 6 — Fixing Bugs / Incorporating Changes: Based on evaluation results, change the software to remove errors. After fixes, re-evaluate to confirm resolution.

The cycle may repeat until all validation criteria are met. The goal is to ensure complete customer satisfaction and that the software fulfills all intended use cases in the appropriate deployment environment.

Q19

Explain Loop Testing with its different types.

Loop Testing is a White Box testing technique specifically designed to test loops, which are fundamental to algorithms and frequently contain errors at their beginning and ending conditions.

Types of Loop Testing:

1. Simple Loops (loop size n): Test cases are designed to:

  • Skip the loop entirely (0 iterations)
  • Only 1 pass through the loop
  • 2 passes through the loop
  • m passes (where m < n)
  • n-1 passes through the loop
  • n+1 passes through the loop (boundary)

2. Nested Loops:

  • Start from the innermost loop
  • Set all outer loops to their minimum iteration count
  • Conduct simple loop tests on the innermost loop
  • Work outward progressively until all loops are covered

3. Concatenated Loops (one after another):

  • If loops are independent: apply simple loop tests to each individually
  • If loops share a loop counter or are not independent: treat them like nested loops

Loop testing is critical because infinite loops, off-by-one errors, and incorrect loop exit conditions are among the most common programming bugs.

Q20

What is a Control Flow Graph? Explain its components.

A Control Flow Graph (CFG) is a directed graph that represents the control structure of a program or module. It is used in Basis Path Testing to identify all possible execution paths.

Components:

  • Nodes (Vertices): Represent sequences of statements or decision points. A node can be a sequential statement, a condition check, or a junction point.
  • Edges (Arrows): Represent the flow of control between nodes — i.e., the path execution takes from one node to another.
  • Junction Node: A node with MORE THAN ONE arrow entering it (convergence point). Example: where if/else branches merge.
  • Decision Node (Predicate Node): A node with MORE THAN ONE arrow leaving it (divergence point). Example: every if, while, for, switch statement.
  • Region: An area bounded by edges and nodes. The area OUTSIDE the entire graph also counts as one region. Number of regions = Cyclomatic Complexity.

Notations used in CFG:

  • Sequential statements → simple flow (one node, one edge)
  • If-Then-Else → branch at decision node, join at junction node
  • While-Do → loop back edge from end to condition node
  • Do-While → loop body first, condition check at end
  • Switch-Case → multiple branches from one decision node
Q21

Explain Manual Testing vs Automation Testing. When should each be preferred?

Manual Testing is where human testers manually execute test cases without automation tools. The tester plays the role of an end-user and identifies unexpected behavior.

Automation Testing is where testers write scripts and use tools (like Selenium, JUnit, TestNG) to automatically execute test cases. Used for re-running scenarios quickly and repeatedly.

Key Differences:

  • Manual: Slower, requires human observation; Automation: Fast, consistent, repeatable
  • Manual: Lower initial cost; Automation: Higher initial investment, lower long-term cost
  • Manual: Best for exploratory, UI/UX, ad-hoc testing; Automation: Best for regression, load, performance testing
  • Manual: Flexible for changing requirements; Automation: Rigid — scripts need updating when UI changes

When to use Manual: First-time testing of new features, exploratory testing, usability testing, complex scenarios requiring human judgment, small projects with tight budgets.

When to use Automation: Repetitive regression tests, load/performance testing, smoke testing with each build, large data volume testing, cross-browser/platform compatibility testing.

Best practice: combine both — automate stable, repetitive tests while using manual testing for complex, exploratory scenarios.

Q22

Explain Condition Coverage and Multiple Condition Coverage with examples.

Both are White Box testing techniques for handling Boolean conditions:

Condition Coverage: All individual conditions within a decision must evaluate to both TRUE and FALSE at least once.

Example: IF (X == 0 || Y == 0) — Two conditions: [X==0] and [Y==0]

  • TC1: X=0, Y=55 → X==0 is TRUE; Y==0 is FALSE
  • TC2: X=5, Y=0 → X==0 is FALSE; Y==0 is TRUE

Only 2 test cases needed. Each condition gets TRUE and FALSE coverage.

Multiple Condition Coverage: ALL possible combinations of condition outcomes must be tested. For n conditions → 2ⁿ test cases required.

Example: Same IF (X == 0 || Y == 0) — n=2 conditions → 2²=4 test cases:

  • TC1: X=0, Y=0 → (TRUE, TRUE)
  • TC2: X=0, Y=5 → (TRUE, FALSE)
  • TC3: X=55, Y=0 → (FALSE, TRUE)
  • TC4: X=55, Y=5 → (FALSE, FALSE)

Key difference: Condition Coverage tests each condition independently; Multiple Condition Coverage tests ALL combinations. Multiple Condition Coverage is more thorough but requires exponentially more test cases. For 3 conditions → 8 test cases; 4 conditions → 16 test cases.

Given Program (Pseudocode):

Nodes and their roles:

V(G) = 2, which is ≤ 10 → Low Risk, Simple Program. Easy to test.

V(G) = 2, so there are 2 independent paths:

  • Path 1: 1 → 2 → 3 → 5 (Both positive: TRUE branch)

An independent path introduces at least one new edge not traversed before.

Q24

Compare Black Box Testing and White Box Testing in detail. Discuss their techniques, advantages, disadvantages, and scenarios where each is appropriate. Provide examples for each technique.

Black Box Testing and White Box Testing are the two fundamental approaches to software testing, representing opposite ends of the testing spectrum in terms of code visibility and tester knowledge.

BLACK BOX TESTING (Behavioral Testing)

Definition: Tests software functionality without any knowledge of internal code structure. Focus is entirely on inputs and outputs based on requirements and specifications.

Techniques:

  • Equivalence Partitioning: Group similar inputs into classes and test one representative. Example: for age validation (1-100), test 50 (valid), -1 (invalid below), 101 (invalid above).
  • Boundary Value Analysis: Test at exact boundaries. For range 10-100: test 9, 10, 11, 99, 100, 101.
  • Cause-Effect Graphing: Model input-output relationships as Boolean graphs. Convert to decision table. n conditions → 2ⁿ test cases.
  • Syntax-Driven Testing: For systems described by grammar (e.g., compilers). Each grammar rule tested at least once.
  • Compatibility Testing: Test across different OS, hardware, browsers.

Advantages of Black Box:

  • No programming knowledge required — domain experts can test
  • Tests from the user's perspective — validates real-world use
  • Unbiased — tester doesn't know implementation details
  • Can detect missing or incorrect requirements
  • Applicable at all levels: unit, integration, system, acceptance

Disadvantages of Black Box:

  • Cannot test internal security vulnerabilities
  • Many paths may remain untested (no visibility into code)
  • Writing test cases without code knowledge can be challenging
  • Low efficiency — may produce redundant test cases

WHITE BOX TESTING (Structural/Glass Box Testing)

Definition: Tests internal code structure, design, and logic. Testers have full access to source code and test specific paths, conditions, and statements.

Techniques:

  • Statement Coverage: Every statement executed ≥ once. Formula: (Executed/Total) × 100%.
  • Branch Coverage: Every TRUE/FALSE branch executed ≥ once.
  • Condition Coverage: Each boolean sub-condition tested as TRUE and FALSE.
  • Multiple Condition Coverage: All combinations tested. n conditions → 2ⁿ test cases.
  • Basis Path Testing: V(G) computed, independent paths identified, one test case per path.
  • Loop Testing: Simple/nested/concatenated loops tested at 0, 1, 2, n-1, n, n+1 iterations.

Advantages of White Box:

  • Thorough — covers all code statements, branches, and paths
  • Optimizes code — removes dead/redundant code
  • Detects hidden security vulnerabilities in code
  • Can start early without requiring a complete interface
  • Easily automated with code coverage tools

Disadvantages of White Box:

  • Expensive — requires expert programmers as testers
  • Cannot detect missing functionalities
  • Code changes require completely rewriting test cases
  • Path coverage with complex programs is practically impossible
  • Tester may inherit developer's blind spots/assumptions

COMPARATIVE TABLE:

Best Practice: Neither approach alone is sufficient. Grey Box Testing — a combination of both — is often used in practice. A skilled tester uses black box testing to verify requirements and white box testing to ensure code quality.

  • Branch Coverage: 100% (both TRUE/FALSE branches of both decisions covered)
  • Path Coverage: 100% of independent paths covered

Conclusion: With just 3 test cases (minimum possible for this program), Basis Path Testing achieves complete coverage. The cyclomatic complexity of 3 confirms low logical complexity. This demonstrates the efficiency of the technique — mathematical derivation guarantees minimum yet complete test case set.

Q30

SCENARIO: Your team followed only Black Box Testing throughout development of a hospital management system. After release, critical bugs were found in the patient billing calculation, prescription validation logic, and drug interaction check code. Analyze this failure. What should have been done differently? Design a hybrid testing strategy for the next version.

Analysis of Testing Failure — Hospital Management System

Root Cause Analysis:

The exclusive use of Black Box Testing is the fundamental flaw. While Black Box testing verified that the system's external behavior matched requirements from a user perspective, it was unable to expose internal logical errors in the code.

  • Billing Calculation Bug: Likely an off-by-one error or incorrect conditional logic in fee calculation code. Black Box testing couldn't see the calculation algorithm — it only observed outputs. White Box testing (especially Statement and Branch Coverage) would have caught this by executing every calculation path.
  • Prescription Validation Logic Bug: Complex nested conditions for dosage limits, drug interactions, and patient allergies — these multi-condition scenarios require Multiple Condition Coverage (2ⁿ test cases) which is a White Box technique. Black Box testing may have missed certain condition combinations.
  • Drug Interaction Check Bug: Critical algorithm failure — the control flow logic for checking multiple simultaneous drugs was likely flawed. Basis Path Testing with Cyclomatic Complexity analysis would have identified all paths through this algorithm and designed test cases for each.

Key Principles Violated:

  • Defect Clustering Ignored: Billing and prescription modules are the most critical (highest risk) — they should have received proportionally more rigorous testing, including White Box techniques.
  • Early Testing Not Applied: Unit testing of individual calculation functions with White Box techniques would have caught these bugs early when they are cheapest to fix.
  • No Formal Technical Reviews: Code review of billing algorithms would have caught logical errors before any testing began.
  • Missing Coverage Metrics: Without White Box testing, the team had no way to know what percentage of the critical code was actually being tested.

REDESIGNED HYBRID TESTING STRATEGY FOR VERSION 2:

Phase 1 — Verification (Pre-Testing):

  • Formal code review of ALL financial and medical calculation modules by senior developers
  • Peer review of prescription validation algorithm and drug interaction logic
  • Static analysis tools (SonarQube) to detect code smells and vulnerabilities
  • IV&V: Independent third-party review for compliance with medical software standards

Phase 2 — White Box Unit Testing (Developer Level):

  • Billing Module: Basis Path Testing — draw CFG, compute V(G). If V(G) > 15, REFACTOR before testing. Achieve 100% branch coverage.
  • Prescription Validation: Multiple Condition Coverage for all drug-dosage condition combinations. With n conditions → design 2ⁿ test cases.
  • Drug Interaction Check: Loop Testing for all medication list iterations. Basis Path Testing for interaction check algorithm.
  • All Financial Calculations: Statement Coverage 100%, Branch Coverage 100%, Condition Coverage for all boolean conditions.

Phase 3 — Black Box Integration Testing:

  • Equivalence Partitioning for patient input fields: valid age ranges, valid medication doses, valid billing amounts
  • Boundary Value Analysis for dosage limits: min dose, max dose ± 1, zero dose, negative dose
  • Cause-Effect Graphing for prescription rules: patient age + diagnosis + drug type → treatment valid/invalid

Phase 4 — System Testing (Independent Team):

  • Performance Testing: Billing for 500 concurrent patients
  • Security Testing: Patient data privacy (HIPAA compliance), unauthorized access prevention
  • Regression Testing: After every bug fix, run automated regression suite

Phase 5 — Validation Testing:

  • Alpha Testing: Hospital administrators and medical staff test in controlled environment
  • Beta Testing: Controlled rollout to 2-3 pilot hospitals for real-world validation
  • UAT: Doctors, pharmacists, billing staff confirm the system meets all workflow needs

Metrics and Success Criteria:

  • Unit test coverage ≥ 95% for all critical modules
  • V(G) ≤ 10 for all modules (refactor if higher)
  • Zero P1 (critical) bugs at beta release
  • All prescription validation paths tested with documented results
  • Independent validation report from third party before go-live

Lesson Learned: In a healthcare system where a bug can directly impact patient safety, no single testing technique is sufficient. The combination of White Box (for code correctness) and Black Box (for requirement validation) with formal reviews provides the highest quality assurance. "Testing shows presence of defects, not their absence" — therefore multiple layers of testing are not redundant but essential for safety-critical systems.

Software Testing · Chapter 3.1 · SE 24CST-208

🎯 Core Definitions

  • ◆Testing = Verify + Validate; find bugs before users do
  • ◆Verification = "Building product RIGHT?" → Static (reviews)
  • ◆Validation = "Building RIGHT product?" → Dynamic (execution)
  • ◆IV&V = Third-party independent validation

📋 5 Key Testing Principles

  • ◆Testing shows presence — NOT absence of bugs
  • ◆Exhaustive testing = IMPOSSIBLE
  • ◆Early testing = cheaper fixes
  • ◆Defect Clustering: 80% bugs in 20% modules
  • ◆Pesticide Paradox: Update test cases regularly!

📊 Testing Levels (In Order)

  • ◆Unit → Dev tests individual modules
  • ◆Integration → Module interaction faults
  • ◆System → Full system, Black Box, pre-release
  • ◆Acceptance → Customer approves before deploy
  • ◆Regression → After every change/fix

🔴 Alpha vs Beta Testing

  • ◆Alpha = Internal team, controlled, developer site
  • ◆Beta = External users, real-world, uncontrolled
  • ◆Alpha uses White Box + Black Box
  • ◆Beta uses Black Box primarily
  • ◆Alpha → Beta → Release (sequence!)

⬛ Black Box Techniques

  • ◆Equivalence Partitioning: Group similar inputs, test 1 per group
  • ◆BVA: Test at boundaries ±1
  • ◆Cause-Effect Graphing: n conditions → 2ⁿ test cases
  • ◆Syntax-Driven: For grammar-based systems
  • ◆Compatibility: OS, browser, hardware testing

⬜ White Box Techniques

  • ◆Statement Coverage: Every statement ≥ once
  • ◆Branch Coverage: Every T/F branch covered
  • ◆Condition Coverage: Each boolean T and F
  • ◆Multiple Condition: ALL combos → 2ⁿ test cases
  • ◆Loop Testing: 0, 1, 2, n-1, n, n+1 iterations

🔢 Cyclomatic Complexity

  • ◆= Number of independent paths = Min test cases
  • ◆Formula 1: V(G) = E – N + 2P
  • ◆Formula 2: V(G) = d + P (d=decisions)
  • ◆Formula 3: V(G) = Regions in flow graph
All 3 formulas give SAME answer!

🚦 Risk Levels V(G)

  • ◆≤ 10 → 🟢 Low Risk, Simple
  • ◆11–20 → 🟡 Moderate Risk
  • ◆21–50 → 🔴 High Risk, Complex
  • ◆> 50 → ⛔ Untestable! REFACTOR!

📐 Basis Path Testing Steps

  • ◆Step 1: Draw Control Flow Graph (CFG)
  • ◆Step 2: Calculate V(G) — all 3 formulas
  • ◆Step 3: Find V(G) independent paths
  • ◆Step 4: Design 1 test case per path
  • ◆Result: 100% statement + branch coverage!
