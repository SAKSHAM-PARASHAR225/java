Slide 3 Introduction to Software Testing

Software testing is the process of verifying whether an application meets its specified requirements and functions correctly under expected conditions.

What it does

Identifies defects, bugs, and functional gaps before deployment — preventing real-world failures.

Why it matters

Detecting issues early significantly reduces development costs and future maintenance efforts.

What it validates

Both functional requirements (does it do the right things?) and non-functional (is it fast, secure, usable?).

🇮🇳 Hinglish
Software testing ek aisa process hai jisme hum check karte hain ki software sahi se kaam kar raha hai ya nahi. Jaise koi naya phone lene ke baad hum uski sari features check karte hain — calling, camera, internet — theek usi tarah software test kiya jata hai. Bugs aur errors dhundhne ke liye ye process zaruri hai.
🇬🇧 Plain English
Just as a car is test-driven before sale, software must be thoroughly tested before release. Testing finds hidden bugs, confirms the software does what it promises, and prevents embarrassing — or dangerous — failures after launch.
Real-Life ExampleWhen a bank's mobile app is developed, testers check if money transfers work correctly, if wrong amounts are rejected, if the app crashes on low battery, and if passwords are stored securely — all before the public release.
Slides 4–5 Software Testing Fundamentals & Key Principles

Testing evaluates software to ensure it performs correctly. It involves both verification (are we building the product right?) and validation (are we building the right product?). It is an integral part of the SDLC.

The 5 Key Principles of Testing:

#PrincipleWhat it means
1Testing shows presence of defectsTesting can reveal bugs but cannot prove there are no bugs at all.
2Exhaustive testing is impossibleYou cannot test every possible input combination — prioritize critical areas.
3Early testingBugs fixed early cost far less than bugs found after release.
4Defect clustering (Pareto Principle)80% of defects are found in 20% of the modules — focus effort there.
5Pesticide ParadoxRunning the same tests repeatedly stops finding new bugs — keep updating test cases.
🇮🇳 Hinglish
Testing ke 5 important principles hain. Pehla — testing sirf bugs dhundh sakti hai, saare bugs ka absence prove nahi kar sakti. Doosra — sab inputs test karna impossible hai. Teesra — jitni jaldi bug dhundho, utna sasta fix hoga. Chautha — Pareto rule: 80% bugs sirf 20% modules mein hote hain. Paanchwa — Pesticide Paradox: wahi test baar baar chalane se naye bugs nahi milenge, isliye test cases update karte raho.
🇬🇧 Plain English
Think of testing like a food quality inspector. They can find contaminated batches but cannot guarantee all food is 100% safe. They focus on high-risk areas (80/20 rule), change their inspection methods to catch new problems (pesticide paradox), and inspect ingredients before cooking (early testing) to save waste.
Exam Tip — Pesticide ParadoxThe pesticide paradox is a frequently asked concept. Remember: if you spray the same pesticide repeatedly, bugs become immune. Similarly, running the same test cases means the software "becomes immune" — no new bugs are found. Solution: regularly update and add new test cases.

Slides 19–21 White-Box Testing

White-box testing (also called glass-box, clear-box, or structural testing) examines the internal code structure, logic, and design. The tester has full access to source code and designs test cases based on program flow.

White-Box Testing — Tester sees everything inside

Statement Coverage Formula
Coverage = (Number of Executed Statements / Total Statements) × 100%
Example: 8 of 10 statements executed → Coverage = 80%
Slides 23–24 Basis Path Testing & Cyclomatic Complexity ⭐ Most Important

Basis Path Testing is a white-box technique that derives a logical complexity measure of procedural design. It uses cyclomatic complexity to determine the minimum number of independent execution paths that must be tested.

Cyclomatic Complexity V(G) is a quantitative measure of the logical complexity of a program, defined by Thomas J. McCabe. It determines how many independent paths exist through the code.

Cyclomatic Complexity Formulas (ALL 3 must be memorized)
Formula 1: V(G) = E - N + 2P
E = Edges, N = Nodes, P = Connected components (usually 1)
Formula 2: V(G) = Number of Regions in flow graph
Formula 3: V(G) = Number of Decision Points + 1
Cyclomatic Complexity Risk Interpretation Table
V(G) ValueRisk LevelInterpretationAction
1 – 10🟢 LowSimple programNormal testing sufficient
11 – 20🟡 ModerateModerate complexityModerate risk, needs attention
21 – 50🔴 HighComplex programMajor restructuring recommended
> 50⛔ Very HighUntestableImmediate refactoring required
Numerical Example — Calculate V(G) Suppose a program has: E = 10 edges, N = 8 nodes, P = 1 component.
V(G) = E – N + 2P = 10 – 8 + 2(1) = 4
This means there are 4 independent paths to be tested.
V(G) = 4 → Low risk, simple program. ✅
🇮🇳 Hinglish
Cyclomatic complexity ek number hai jo batata hai ki code mein kitne alag-alag raaste hain. Jaise ek city mein different roads hain — koi bhi destination tak 4 tarike se ja sakte ho. Toh V(G) = 4 matlab 4 alag test cases banana padenge. Zyada complex code mein zyada raaste hain, isliye testing mushkil ho jaati hai.
🇬🇧 Plain English
Cyclomatic complexity is like counting the number of different routes through a road map (the program). If there are 4 different paths through the code, you need at least 4 test cases to cover all paths. Higher complexity = more paths = harder to test completely.
Most Important Exam Points (1) The formula V(G) = E – N + 2P appears in almost every exam. (2) Decision Points formula = number of IF/WHILE/FOR decisions + 1. (3) V(G) also equals the number of independent paths that must be tested. (4) For a single-component graph, P = 1.

Slides 8–10 Software Reliability & Metrics

Software reliability is the probability of failure-free operation for a specified period of time in a specified environment. Unlike hardware, software does not wear out physically — it fails due to design defects.

Key Reliability Formulas — All must be memorized
MTBF = Total Operating Time / Number of Failures
Mean Time Between Failures — average time between consecutive failures
MTTF = Total Operating Time / Total Failures
Mean Time To Failure — average time to first failure in new systems
MTTR = Total Repair Time / Number of Repairs
Mean Time To Repair — average time to fix a failure
Availability = MTBF / (MTBF + MTTR)
Percentage of time the system is operational
Failure Rate = Number of Failures / Operating Time
Numerical Example — Reliability Calculation A server runs for 1000 hours and has 5 failures. Total repair time = 10 hours.
MTBF = 1000/5 = 200 hours (fails once every 200 hours on average)
MTTR = 10/5 = 2 hours (each repair takes 2 hours)
Availability = 200/(200+2) = 200/202 ≈ 99.01%

Reliability Models:

ModelKey Assumption
Jelinski-MorandaConstant failure rate for each remaining defect
Goel-OkumotoUses non-homogeneous Poisson process for predictions
Musa's Basic Execution TimeRelates failures directly to execution time
Schneidewind ModelUses least squares estimation for reliability prediction
Littlewood-VerrallVariable failure rate for each individual defect

Slides 4–6 Introduction to Software Maintenance

Software maintenance is the systematic process of modifying a software product after its initial delivery to correct faults, improve performance, and adapt to changing requirements.

Key Statistic — Exam Favourite!Software maintenance represents 60 to 70% of total software lifecycle costs. This means more money is spent maintaining existing software than building new software.

Why is maintenance needed?

🐛 Error Correction

Bugs found during real-world operation need fixing

🔄 Requirement Changes

User needs evolve — software must keep up

⚡ Performance Improvement

Optimize speed and efficiency over time

🛡️ Security Updates

New vulnerabilities emerge and must be patched

📜 Regulatory Compliance

Laws and standards change, software must comply

🇮🇳 Hinglish
Software maintenance matlab — jaise ek car khareedne ke baad petrol bhar, tyre change karo, servicing karao — ye sab maintenance hai. Software bhi bana ke chod nahi sakte. Bugs aate hain, nayi features chahiye hoti hain, aur operating system change hota hai — toh software ko update karte rehna padta hai. Aur ye sab total cost ka 60-70% le leta hai!
🇬🇧 Plain English
Think of a smartphone. You bought it once, but you keep updating the OS, patching security holes, installing new apps, and upgrading storage. Similarly, once software is deployed, it constantly needs care — bug fixes, new feature additions, compatibility with new hardware, and security patches. This ongoing work is software maintenance.

Slides 17–22 Software Maintenance Models
⚡ Quick Fix Model

Fastest approach — immediate fix without full analysis. High risk of introducing new bugs. No documentation update. Used for emergency situations only. Should be followed by proper permanent solution.

🔄 Iterative Enhancement Model

System enhanced through multiple planned iterations. Each iteration adds features properly. Documentation updated after each cycle. Maintains system integrity through proper analysis-design-test phases.

📦 Reuse-Oriented Model

Uses existing proven components from a repository. Reduces development time and cost. Improves quality by reusing tested components. Requires well-organized component library.

📊 Boehm's Model

Risk-based analysis to prioritize tasks. Considers cost, schedule, and technical challenges. Balances corrective and enhancement work. Structured decision-making through risk assessment.

2MDifferentiate between Verification and Validation.
▼ Show Answer
Verification asks "Are we building the product right?" — it is a static process using reviews and inspections to check conformance to specifications. Validation asks "Are we building the right product?" — it is a dynamic process involving actual test execution to ensure the product meets user needs. Verification happens first, validation happens after.
2MWhat is the Pareto Principle in software testing?
▼ Show Answer
The Pareto Principle (also called Defect Clustering) states that 80% of software defects are concentrated in just 20% of the modules. This means testing effort should be focused on these high-risk, defect-prone modules to maximize defect detection efficiency rather than testing all modules equally.
2MWhat are the four types of software maintenance? Give the percentage effort for each.
▼ Show Answer
(1) Corrective: Fixing bugs after deployment — 20% effort. (2) Adaptive: Modifying for new environments (OS/hardware changes) — 25%. (3) Perfective: Improving performance and adding features — 50% (largest). (4) Preventive: Refactoring to prevent future problems — 5% (smallest).
2MWhat is reverse engineering in software? State its purpose.
▼ Show Answer
Software reverse engineering is the process of systematically analyzing existing software to identify its components and understand their interrelationships by examining source code. Its purposes include: recovering lost documentation, understanding legacy systems, facilitating migration to new technologies, supporting interoperability, and enabling effective maintenance of complex systems.
2MState the formula for Availability in software reliability.
▼ Show Answer
Availability = MTBF / (MTBF + MTTR)
Where MTBF = Mean Time Between Failures and MTTR = Mean Time To Repair.
Example: MTBF = 200 hrs, MTTR = 2 hrs → Availability = 200/202 = 99.01%. This represents the percentage of time a system is operational.
3 5-Mark Questions
5MExplain Black-Box Testing techniques with examples.
▼ Show Answer

Black-box testing examines software functionality WITHOUT knowledge of internal code. Key techniques:

1. Equivalence Partitioning: Divides input data into valid and invalid classes. E.g., for age input (18–60): valid = {25}, invalid = {10}, {70}. Reduces number of test cases.

2. Boundary Value Analysis: Tests at exact boundary edges. For age 18–60: test 17, 18, 60, 61. High defect rate at edges.

3. Decision Table Testing: Tests all combinations of conditions. E.g., login: correct username + correct password = success; wrong password = fail.

4. State Transition Testing: Tests behavior changes between states. E.g., bank account: Normal → Locked after 3 wrong PINs → Unlocked after verification.

5. Use-Case Testing: Tests complete user workflows. E.g., e-commerce: browse → add to cart → checkout → payment → order confirmation.

5MExplain SEI-CMM maturity levels in detail.
▼ Show Answer

SEI-CMM (Software Engineering Institute Capability Maturity Model) has 5 levels:

Level 1 – Initial: Processes are ad-hoc and chaotic. Success depends on individual heroics, not processes. No planning or management structure.

Level 2 – Repeatable: Basic project management is established. Requirements, planning, tracking, and configuration management in place. Processes are disciplined but project-specific.

Level 3 – Defined: Organization-wide standard processes documented and used across all projects. Includes process definition, training, peer reviews, and integrated management.

Level 4 – Managed: Quantitative measurement and statistical control of processes. Metrics drive all decisions. Both software quality management and process management are quantitative.

Level 5 – Optimizing: Continuous improvement through innovation, defect prevention, and technology change management. Focus is on preventing defects proactively and improving processes continuously.

Key Point: Each level builds upon the previous level. Organizations must achieve all lower levels before advancing. Major IT companies like TCS, Infosys are CMM Level 5 certified.

5MExplain Formal Technical Review (FTR) — its process, roles, and importance.
▼ Show Answer

Definition: FTR is a structured software review with predefined roles, documented procedures, and formal findings.

Roles: (1) Moderator — plans, facilitates, controls the meeting. (2) Author — presents work product. (3) Reviewer — finds defects and suggests improvements. (4) Recorder — documents all issues. (5) Manager — ensures resources (NO evaluation role).

Process: Review request → Planning → Individual preparation → Review meeting (2–4 hrs max) → Issue recording → Rework and follow-up.

Importance: Reviews find defects much earlier and cheaper than testing. Studies show defects found in reviews cost 10x less to fix than defects found in testing, and 100x less than production defects. Also promotes knowledge sharing and standards adherence.

4 10-Mark Questions
10MExplain software testing strategies, levels, and their objectives in detail. Also explain white-box testing techniques.
▼ Show Answer

Testing Strategy: A high-level plan defining scope, objectives, resources, and methods throughout the SDLC. It aligns with the development lifecycle and ensures systematic testing.

Testing Levels (5 levels):

1. Unit Testing: Tests individual components (functions/methods) in isolation. Done by developers in early phase. Finds logic errors at smallest level.

2. Integration Testing: Tests combined modules working together. Done by testers after unit testing. Finds interface defects between modules.

3. System Testing: Tests complete software system against all requirements (functional + non-functional). Done by test team pre-release. Includes functional, performance, security, usability, compatibility testing.

4. Acceptance Testing: Final user-driven testing before deployment. Alpha testing (internal, controlled) and Beta testing (external, real users). Done by customers.

5. Regression Testing: Re-testing after modifications to ensure no new bugs were introduced. Done by QA team after every change.

White-Box Testing Techniques:

1. Statement Coverage: Ensures every executable statement runs at least once. Formula: (Executed/Total)×100.

2. Branch Coverage: Every decision's true and false branches must execute. Better than statement coverage.

3. Condition Coverage: Each Boolean sub-condition evaluates both T and F.

4. Path Coverage: Tests all independent execution paths — most thorough but exponentially complex.

5. Basis Path Testing + Cyclomatic Complexity: V(G) = E – N + 2P determines minimum paths to test. V(G) ≤ 10: simple, V(G) 11-20: moderate, V(G) 21-50: complex, V(G) > 50: untestable.

10MExplain software maintenance types, reverse engineering, and software reuse with approaches.
▼ Show Answer

Software Maintenance Definition: Systematic modification after delivery to correct faults, improve performance, adapt to environment. Costs 60-70% of total lifecycle.

4 Types: (1) Corrective — bug fixes, 20%. (2) Adaptive — environment changes, 25%. (3) Perfective — new features, 50%. (4) Preventive — refactoring, 5%.

Reverse Engineering: Analyzing existing code to recover lost design info, understand legacy systems, and facilitate migration. Levels: Implementation (code) → Design (architecture) → Requirements (functionality) → Domain (business logic). Process: Acquire → Analyze → Extract → Abstract → Document.

Maintenance Models: Quick Fix (fast, low quality), Iterative Enhancement (planned, good quality), Reuse-Oriented (component-based, fast and quality), Boehm's (analytical, highest quality).

Software Reuse: Using existing artifacts in new development. Issues: Technical (integration), Organizational (resistance), Economic (cost), Legal (licensing), Quality (reliability). Approaches (least to most systematic): Ad-hoc → Systematic → Component-based → Application Family → Framework-based.

5 Scenario-Based Questions
ScenarioA hospital's new patient management system crashes when two nurses try to update the same patient record simultaneously. Which type of maintenance is needed? Justify.
▼ Show Answer
Answer: Corrective Maintenance.
The system is crashing due to a concurrency bug (two simultaneous updates) discovered after deployment. Corrective maintenance addresses bugs and errors found during actual operational use. The team would apply an emergency fix — implementing proper database locking or transaction management — then follow up with thorough testing. This is reactive, triggered by a discovered failure.
ScenarioA company writes the same database connection code in every new project. A developer suggests building a centralized library. Which reuse approach is this? What are the challenges?
▼ Show Answer
Answer: Moving from Ad-hoc Reuse to Systematic/Component-Based Reuse.
Currently, the team practices ad-hoc reuse (informal copying of code). The developer's suggestion is to establish systematic reuse with a centralized component repository. Challenges include:
• Technical: Ensuring the library works across different project contexts (integration compatibility).
• Organizational: Getting developers to change habits and use the library instead of writing their own code (cultural resistance).
• Economic: Initial investment in building, documenting, and maintaining the library.
• Quality: Ensuring the library component is reliable and well-tested for all use cases.
Long-term benefit: Significant reduction in development time and consistency across projects.
ScenarioCalculate cyclomatic complexity: A program's flow graph has 12 edges, 9 nodes, and 1 connected component. Is this safe to deploy?
▼ Show Answer
Calculation:
V(G) = E – N + 2P = 12 – 9 + 2(1) = 3 + 2 = 5
Interpretation: V(G) = 5 falls in the range 1–10 → Low Risk, Simple Program.
This means there are 5 independent paths to test. Since V(G) ≤ 10, the program has low complexity and normal testing is sufficient. Yes, it is relatively safe to deploy after testing all 5 independent paths.
6 Twisted / Conceptual Questions
Twisted"Testing can prove that software is completely bug-free." True or False? Justify fully.
▼ Show Answer
FALSE. This relates to the first principle of testing: "Testing shows the presence of defects but cannot prove their absence." Even after extensive testing, no tester can guarantee that ALL bugs have been found. Exhaustive testing (testing every possible input combination) is impossible for real systems. A calculator with just two 32-bit integer inputs would require 2^64 test cases — impossible to run. Testing reduces risk and increases confidence but cannot provide absolute proof of zero bugs. Quote: "Program testing can be used to show the presence of bugs, but never to show their absence." — Dijkstra.
TwistedCan a company at CMM Level 1 still deliver good software? Why or why not?
▼ Show Answer
Yes — but not reliably or repeatedly. CMM Level 1 (Initial) means processes are ad-hoc and chaotic. Success depends on individual heroics and exceptional personal effort. A talented team or single brilliant developer CAN deliver good software at Level 1, but the key issue is repeatability. Next project, if the same hero is unavailable or tired, the quality drops. At Level 1, you cannot predict outcomes, cannot guarantee delivery dates, and cannot scale. CMM exists to ensure quality comes from processes, not individuals, making success repeatable and independent of who is on the team.
TwistedWhy does perfective maintenance (50% effort) dominate over corrective maintenance (20%)? Should companies be worried?
▼ Show Answer
Perfective maintenance dominates because in mature software that is working correctly, most effort is spent improving and extending the product — adding new features, optimizing performance, improving UX — driven by user demand and market competition. Low corrective maintenance (20%) actually signals good quality — it means the software had few bugs after release. Companies should NOT be worried by high perfective maintenance; it is a sign of a successful, in-demand product. Worry would arise if corrective maintenance is high (many bugs) or if preventive maintenance is zero (technical debt accumulating).
7 Viva Questions & Answers
Q: What is the difference between a bug, defect, and failure?
A: Bug = error in code (developer mistake). Defect = deviation from requirement (found during testing). Failure = software unable to perform its function (observed by user in production).
Q: Why is P usually 1 in cyclomatic complexity formula?
A: P = number of connected components in the flow graph. A typical single program/function has just one connected component, so P = 1. For multiple procedures, P would be higher.
Q: What is the difference between software reliability and hardware reliability?
A: Hardware wears out physically over time (bathtub curve). Software does not have physical wear — it fails due to design defects. Software reliability improves as bugs are removed but can degrade if bad maintenance introduces new bugs.
Q: Can you perform white-box testing on a closed-source application?
A: No — white-box testing requires access to source code. For closed-source software, only black-box testing is possible since the internal workings are hidden. This is why third-party testers typically use black-box techniques.
Q: Why is the moderator's role most important in FTR?
A: The moderator plans the review, ensures the right people attend, keeps the meeting focused on technical issues (not personal criticism), enforces the 2-4 hour time limit, and ensures action items are properly tracked. Without effective moderation, reviews degenerate into unproductive discussions.
